1.1Why Swap Tokenizers

From two trained word-vocabularies to one pretrained BPE encoder

The original notebook (Part 3.1 of the blueprint) builds two separate vocabularies from scratch — one for German, one for English — by running spaCy over the entire Multi30k corpus and counting token frequencies. That's accurate, but it's also work: a tokenizer download, a full pass over the dataset, and a min_freq threshold to tune. This edition replaces all of that with tiktoken's cl100k_base encoding — the same byte-pair-encoding scheme behind GPT-3.5/4 — which already knows how to tokenize dozens of languages, German and English included, with no training pass required.

ORIGINAL — spaCy + custom Vocab
  • Separate DE and EN tokenizer models
  • Word-level tokens, built from this corpus only
  • Vocabulary built by counting frequencies across train/val/test
  • <unk> absorbs anything below min_freq
TIKTOKEN — one BPE encoder, both languages
  • Single cl100k_base encoder reused for DE and EN
  • Subword tokens, pretrained on a massive general corpus
  • Vocabulary is fixed and instant — nothing to build
  • No real <unk> — BPE can always fall back to bytes
Why this matters

Word-level vocabularies are corpus-dependent and brittle — a word Multi30k never saw becomes <unk>, permanently unrecoverable. Subword BPE tokenization can always decompose an unfamiliar word into smaller known pieces (or, worst case, raw bytes), so out-of-vocabulary words essentially stop existing as a category of failure.

2.1load_tokenizers()

One encoder, returned twice

Where the original had two separate load(de) / load(en) calls, this version loads a single universal encoder and hands it back for both slots — deliberately, so the rest of the pipeline still works with an "encoder_de, encoder_en" pair without needing to know they're the same object.

load_tokenizers()
def load_tokenizers():
    """
    Loads the universal tiktoken BPE encoder.
    Returns the same encoder instance for both German and English slots
    to preserve compatibility with the rest of your pipeline.
    """
    # 'cl100k_base' handles German, English, and dozens of other languages natively.
    # (If using GPT-4o style processing, you can use "o200k_base" instead)
    encoder = tiktoken.get_encoding("cl100k_base")

    # Returning the encoder twice so downstream code that expects
    # tokenizer_de, tokenizer_en = load_tokenizers() keeps working unchanged
    return encoder, encoder
Why this matters

Because both languages already share representation space through the same BPE merges, a word or subword that looks similar across German and English (proper nouns, cognates, punctuation) can end up mapping to identical or overlapping token IDs — something two independently-trained word vocabularies would never produce.

2.2TiktokenVocabWrapper

Making a BPE encoder look like the old Vocab class

Every downstream function in the notebook — collation, batching, the training loop — was written against a Vocab object with .stoi, __getitem__, and __call__. Rather than touch that code, this wrapper gives tiktoken's encoder the same interface.

TiktokenVocabWrapper
class TiktokenVocabWrapper:
    """
    A lightweight vocabulary wrapper around tiktoken to mimic the original
    Vocab class structure, preventing breaks in later code blocks.
    """
    def __init__(self, encoder):
        self.encoder = encoder
        # minimal fallback maps for any code that accesses .stoi / .itos explicitly
        self.stoi = {self.encoder.decode([i]): i for i in range(min(5000, self.encoder.n_vocab))}
        self.itos = {i: self.encoder.decode([i]) for i in range(min(5000, self.encoder.n_vocab))}

    def __getitem__(self, token):
        if isinstance(token, int):          # already an id -> pass through
            return token
        if token == "<blank>":
            return self.encoder.eot_token   # reuse end-of-text as the padding id
        try:
            return self.encoder.encode_single_token(token)
        except ValueError:
            return self.encoder.eot_token

    def __call__(self, tokens):
        if isinstance(tokens, list) and tokens and isinstance(tokens[0], int):
            return tokens                   # already ids -> no-op
        if isinstance(tokens, str):
            return self.encoder.encode(tokens)
        return [self.__getitem__(t) for t in tokens]

    def __len__(self):
        return self.encoder.n_vocab

    def get_stoi(self):
        return self
Key insight

This is an adapter, not a reimplementation — it exists purely so Batch, collate_batch(), and every other consumer of "vocab-shaped" objects downstream can keep calling vocab(tokens) or vocab[token] without caring that the real work is now delegated to tiktoken's BPE encoder. One notable design choice: <blank> is mapped onto tiktoken's own end-of-text token rather than getting a dedicated padding id, since BPE vocabularies don't ship with one.

2.3load_vocab()

Instant vocabulary — no corpus pass required

load_vocab()
def load_vocab(encoder_de, encoder_en):
    """
    Replaces the heavy dataset counting and loading logic.
    Instantly returns wrapped tiktoken encoders mimicking vocab objects.
    """
    print("Initializing tiktoken BPE Vocabularies...")

    vocab_src = TiktokenVocabWrapper(encoder_de)
    vocab_tgt = TiktokenVocabWrapper(encoder_en)

    print("Finished.\nVocabulary sizes (Fixed BPE Boundaries):")
    print(f"Source (DE): {len(vocab_src)}")
    print(f"Target (EN): {len(vocab_tgt)}")
    return vocab_src, vocab_tgt

Compare this to the original's build_vocab_from_iterator(), which had to tokenize every sentence across train, validation, and test splits just to count frequencies before a single vocabulary entry existed. Here, len(vocab_src) and len(vocab_tgt) are both just encoder.n_vocab — a fixed, pre-baked number, known before any data is even loaded.

3.1create_dataloaders()

Same collation logic, BPE tokenize functions underneath

The batching and padding machinery — collate_batch(), DistributedSampler, the DataLoader construction — is untouched from the original. Only the tokenize functions handed into it change, and the padding id now comes from tiktoken directly instead of a vocabulary's reserved <blank> index.

create_dataloaders() — the tiktoken-specific parts
def create_dataloaders(
    device,
    encoder_de,     # tiktoken encoder
    encoder_en,     # tiktoken encoder
    vocab_src,      # TiktokenVocabWrapper for source (DE)
    vocab_tgt,      # TiktokenVocabWrapper for target (EN)
    batch_size=12000,
    max_padding=128,
    is_distributed=True,
):
    def tokenize_de(text):
        return encoder_de.encode(text)     # straight BPE encode, no spaCy step

    def tokenize_en(text):
        return encoder_en.encode(text)

    pad_id = encoder_de.eot_token           # end-of-text id stands in for <blank>

    def collate_fn(batch):
        return collate_batch(
            batch, tokenize_de, tokenize_en, vocab_src, vocab_tgt,
            device, max_padding=max_padding, pad_id=pad_id,
        )
    # Multi30kDataset, DistributedSampler and DataLoader construction: unchanged
Analogy

Think of collate_batch() as a conveyor belt that doesn't care what machine hands it parts — swap the spaCy tokenizer for tiktoken's encode(), and the belt keeps running exactly the same way, just fed by a different upstream station.

3.2check_outputs()

Decoding predictions back to readable text

Where the original walked Vocab.itos to turn predicted ids back into words, this version calls encoder.decode() directly — and has to explicitly strip tiktoken's end-of-text marker from the tail of the generated output, since it doubles as the padding token.

check_outputs() — decoding side
pad_idx = encoder_de.eot_token

src_ids = [int(x) for x in rb.src[0] if x != pad_idx]
tgt_ids = [int(x) for x in rb.tgt[0] if x != pad_idx]

src_text = encoder_de.decode(src_ids).replace("\n", "")
tgt_text = encoder_en.decode(tgt_ids).replace("\n", "")

model_out = greedy_decode(model, rb.src, rb.src_mask, 72, pad_idx)[0]
model_out_ids = [int(x) for x in model_out if x != pad_idx]
model_txt = encoder_en.decode(model_out_ids).split("<|endoftext|>", 1)[0]
Why this matters

Because subword tokens don't map one-to-one with whitespace-separated words, encoder.decode() is doing real reconstruction work here — stitching BPE pieces back into readable text — in a way the original's word-level itos lookup never had to.

3.3The Parameter Cost Tradeoff

What a bigger, shared vocabulary actually costs

The original blueprint's embedding and generator layers were sized against two corpus-specific vocabularies — roughly 60K German tokens and 37K English tokens (3.5 of the blueprint). cl100k_base is a general-purpose vocabulary of roughly 100K tokens, used twice — once for the source embedding table, once for the target — plus once more in the generator's output projection.

layeroriginal (word vocab)tiktoken (cl100k_base)
Source embedding~60K × 512 ≈ 31M~100K × 512 ≈ 51M
Target embedding~37K × 512 ≈ 19M~100K × 512 ≈ 51M
Generator projection512 × 37K ≈ 19M512 × 100K ≈ 51M
I/O layers total≈ 69M≈ 153M
Worth knowing before you swap tokenizers

Convenience has a real memory cost here: a vocabulary built to serve every language cl100k_base supports is far larger than one built for exactly this dataset, so the embedding and generator layers alone roughly double in size — on top of the ~19M/25M encoder/decoder-stack parameters that stay identical either way (3.5 of the original blueprint). For a small dataset like Multi30k, most of that vocabulary is never actually exercised during training.

Analogy

It's the difference between stocking a pantry with exactly what one recipe needs versus keeping a pantry stocked for every recipe in a cookbook — the second is more convenient the next time you cook something new, but you're paying storage cost for ingredients this particular dish never touches.
